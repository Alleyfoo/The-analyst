# Central state model

This inventory covers every `types.ts::GameState` field. Initial values come from `types.ts::INITIAL_STATE`; writes come from `hooks/useGameEngine.ts::useGameEngine` actions/update loop and `constants.ts` effects. All fields below are serialized to `the_analyst_save_v1`, even derived values. Persistence does not imply validation or an invariant enforced on every write.

S0 added persisted expansion progression, S1 the organisational handoff, S2 one assistive SQL trial, S3 a finite review queue, G1 an Ascension boundary, S4 continuous SQL demand, S5 accelerated routing/explicit Acceleration establishment, S6 two schema exception batches, S7 local Product DB read context/Connected Enterprise, S8 a bounded five-write pilot, S9 recurring human-approved Product DB writebacks, S10 bounded write policy/Good Enough, S11 aggregate batch routing/Lightspeed, S12 source-drift quarantine/Governance-Crisis, S13 an authored root-cause investigation, S14 a governed source-contract repair, S15 an executive review/organisational rollout acknowledgement, and S16 two role endings. Original resource/update rules remain unchanged. The design authority remains [AI_EXPANSION.md](../design/AI_EXPANSION.md), whose baseline evidence describes the pre-S0 snapshot.

## Derived versus persistent

The source does not separate a save schema from runtime state. Complexity, observability, packet loss, price deltas and chart snapshots are derived **and** persisted. World economy and entropy are evolved accumulators. Rates and resource totals persist directly rather than being rebuilt from `upgrades`. `prestige.multiplier` duplicates a derived expression but the engine uses `1 + level*0.1` instead (`useGameEngine` main interval and reward actions).

Transient unsaved values include `stateRef`, hook-local `isRebooting`, App's `pilotOpen`, Workstation tab/floating messages, TeamComms open state, DataStream boot state and all minigame local scores/boards/canvas data. S2's engine attempt ID/sequence refs and SQL draft/preparation/timer refs are unsaved. Engine-returned `pilotIntroduction` and `sqlPilotAvailable` are derived, not saved fields. `DashboardPanel` computes funnel impressions as `rawData*10` and campaign totals from active campaigns; these are UI derivations, not central fields.

## localStorage boundary

The sole localStorage key and all read/write/remove sites are in `hooks/useGameEngine.ts`: initializer read, two-second autosave write, `ascend` immediate write and `hardReset` removal. No source writes API configuration or independent component settings to localStorage. Hydration preserves unknown top-level JSON fields by spreading `parsed`; it restores selected nested defaults/functions and does not validate existing numeric ranges. S1 uses the era/transition object below; there is no save version field or completed-run history.

## Expansion progression authority (S0/S1/S2)

`types.ts::EXPANSION_ERAS` defines `analyst`, `automation`, `ai_pilot`, `acceleration`, `connected_enterprise`, `good_enough`, `lightspeed`, and `governance_crisis`; `ExpansionEra` derives its union from that list. `ExpansionProgress` contains only `era` and `transition`. Purpose-specific queue/demand counters live separately below; no Velocity, verification, permissions or provenance system exists.

`hydrateState` merges default progression with saved fields. A missing or unsupported era defaults to `analyst`, regardless of PU/TU, prestige, upgrades or tick. Missing/null transition defaults to null; incomplete/invalid transitions are discarded unless they contain a known `targetEra` and string `step`. Valid transition objects and unknown saved progression fields are preserved. This validation is confined to the new object; it is not a general migration framework and does not repair existing hydration quirks.

`useGameEngine::beginExpansionTransition(targetEra, step)` refuses a same-era target, blank step, replacement of a pending transition or an already-open Ascension. S1 restricts `ai_pilot` starts to eligible analysts at `automation_recognized`. `establishExpansionEra(targetEra)` requires a matching pending target; generic `ai_pilot` establishment remains refused because S3 owns its result acknowledgement. Neither generic action is passed to UI. `advancePilotIntroduction(expectedStep)` guards against stale/double acknowledgements and active baseline overlays; the narrow SQL actions are described below.

The existing whole-state autosave serializes progression without changing the save key. Reconstruction from INITIAL_STATE returns progression to analyst/null. G1 adds the derived ending gate below without changing prestige calculations or factory reset.

S0 validation: npm ci/build/lint passed. Isolated browser smoke passed fresh autosave/reload, ordinary and high-score legacy saves, partial objects, valid future transitions, invalid-era fallback and unknown-field preservation. A temporary deterministic hook/timer harness compared original baseline fresh state plus 20 ticks and found exact equality excluding only progression; it also checked guarded actions. This is limited validation, not an exhaustive gameplay regression suite.

## AI pilot introduction (S1)

Eligibility is exactly three true purchase flags: `pandas_scripts`, `sql_optimization`, `local_server` (`constants.ts::isAIPilotEligible`). These establish existing pipeline/query/storage investment, without new usage counters or claims that minigames were completed. Python ETL costs 50 PU and appears at raw >200; SQL costs 200 PU at clean >500; server costs 150 PU at raw >450 (`UPGRADES`, `checkUpgradeVisibility`). All are reachable through ordinary Act I cleaning/inflow/storage and scripts/mapping. No model, KPI, segmentation, ending or score threshold is required; no upgrade was rebalanced.

`useGameEngine` offers the transition when eligible with `era='analyst'` and no pending transition. `types.ts::AI_PILOT_STEPS` supplies stable identifiers:

| Step | Era | Explicit player acknowledgement |
| --- | --- | --- |
| `automation_recognized` | `analyst` | Recognize existing automation, advance to `automation` / `pilot_announced` |
| `pilot_announced` | `automation` | Acknowledge approved enterprise trial, advance to `pilot_ready` |
| `pilot_ready` | `automation` | S1 end state; S2 now offers the SQL trial, no era establishment |
| `pilot_success` | `automation` | Successful assisted SQL execution; review positive feedback to advance |
| `demand_pending` | `automation` | Review PILOT EXPANSION; acknowledgement creates three queued requests |
| `rollout_review` | `automation` | Explicitly review/execute three queued requests; last completion advances `rollout_success` |
| `rollout_success` | `automation` | Acknowledge queue result; establishes `ai_pilot`, clears transition, starts six requests |

Steps use the existing two-second whole-state autosave. Reload restores the saved step and leaves its dialog closed; unsaved acknowledgements within the ordinary autosave window may be repeated. Unknown valid future step strings remain preserved by hydration but are not presented as S1 content. High-score legacy saves default to analyst; an eligible legacy purchase combination offers recognition, never skips the narrative.

UI entry: `Workstation` shows a management-update button across tabs, using engine-derived `pilotIntroduction`; `App` opens `AIPilotIntroduction` only on request. “Later” closes presentation without clearing progression. The engine disables presentation/advancement during any minigame, coffee, meeting, baseline event, blocking task, ascension or reboot. A new blocker closes the dialog; the same step can be reopened afterward. Baseline `EVENTS`, `eventHistory`, effects and simulation continue unchanged. Pilot-ready points to SQL; pilot-success offers “Review pilot result”; demand-pending now offers the S3 expansion review. No AI reward bonus or Velocity exists.

Focused validation: `node scripts/check-ai-pilot.cjs` uses installed TypeScript and Node with stubbed hooks/timers; browser smoke covers actual UI, saves and reloads. It is not an exhaustive baseline gameplay suite.

## First assistive SQL trial (S2)

`useGameEngine::isSQLPilotReady` derives availability only at `automation / ai_pilot / pilot_ready`. Open the unchanged Workstation SQL activity normally. `SQLMiningGame` captures availability at window opening and exposes USE AI PILOT only for that trial. Its 700 ms local timer copies the current existing `REQUESTS[].required` solution into the same query/editor; the original prefix-based preview updates naturally. No API, LLM or new task generator is involved. Manual clause controls remain usable; the ordinary exact-sequence success rule and human EXECUTE click remain required.

`beginSQLPilotAttempt` issues one transient numeric attempt ID only while SQL is open and progression is ready, outside blocking tasks/ascension/reboot. Preparing a draft changes no central resource or step. After a correct human execution, SQL's existing 1500 ms success presentation calls `completeSQLPilotQuery(attemptId)`. That action checks the current exact progression, open SQL mode and matching engine-issued ID. It atomically applies the shared `sqlQueryReward` and advances to `pilot_success`; changed progression prevents repeat rewards. `completeSQLQuery` remains the ordinary reward-only path and cannot advance the pilot.

Reward equivalence: both paths grant 100 clean data and 250 PU multiplied by `1+0.1*prestige.level`, log the original query-success message, and contribute the same multiplied PU to an active board meeting. No TU, rate, entropy, resource cost or bonus is added. Meeting activity does not prevent executing the SQL trial; it defers management feedback. Once EXECUTE has occurred, completion uses the same economic timing as ordinary SQL, including completion during a later blocking task; the existing close-toggle behavior remains unchanged.

New pilot timers are cancelled on close/inactivation. Closing before confirmation (including after draft preparation) grants nothing and leaves `pilot_ready`; this does not repair baseline manual SQL's uncancelled success timer. Reload discards unfinished local drafts/IDs and permits retry. `pilot_success` and `demand_pending` persist through the same two-second autosave; the original unsaved-window limitation still applies. Feedback is opt-in, positive, and acknowledgement-only: it changes `pilot_success -> demand_pending`, with era/target unchanged. S3 continues from that checkpoint below.

## Finite pilot workload (S3)

`GameState.aiReviewQueue` (`types.ts`) persists `{ pending: number, completed: number, wave: number }`. Fresh/legacy defaults are `{ pending: 0, completed: 0, wave: 0 }`; hydration restores each nonnegative safe integer, otherwise zero. Completed counts are **per wave**. No scores infer queue state. The first acknowledged expansion sets `{3,0,1}`; each successful review decrements pending and increments completed; the acknowledged first-wave result sets `{6,0,2}`. Both waves remain finite. S4 offers operational rollout only after the second six are reviewed. Partial malformed saves receive field defaults, not a general migration/repair system.

`advancePilotIntroduction` accepts expansion only at `automation / ai_pilot / demand_pending` with wave zero. The first queue is active only at `automation / ai_pilot / rollout_review`, wave one. After all three are paid, `rollout_success` persists with `{0,3,1}`; its acknowledgement alone sets era `ai_pilot`, transition null and the six-request second wave. Generic `establishExpansionEra('ai_pilot')` remains refused.

`Workstation` exposes counts and REVIEW NEXT QUERY. `openNextAIReview` requires the active queue and clear activity/presentation guards, then opens ordinary SQL and issues a temporary ID tied to wave/completed count. `SQLMiningGame` chooses a usual random request and prepares its correct clauses after 700 ms. The editor/preview remain editable; exact valid human EXECUTE schedules the existing 1500 ms success delay through the separate `completeAIReviewQuery` callback. That engine action requires active progression, positive pending, open SQL, matching issued ID/wave/completed snapshot, and atomically pays one unchanged SQL reward while consuming one request. Repeated/stale callbacks cannot consume later requests. Manual `completeSQLQuery` never touches the queue.

Every queue reward is exactly 100 clean +250 PU, prestige-scaled, with the original meeting contribution/log. No rate, TU, entropy or other baseline formula changes. Temporary IDs, drafts and SQL queue context are not saved; close/inactivation cancels new timers without consumption. A reload of open SQL restores its ordinary persisted mode with an empty manual editor; close it and select REVIEW NEXT QUERY to retry the preserved queue. This never regenerates completed work. The two-second unsaved window applies to rewards/acknowledgements as before. Already-executed completions follow original reward timing if a blocker intervenes; management stays deferred. Factory reset reconstructs INITIAL_STATE and clears queue/progression; G1 prevents new gameplay Ascension during expansion.

## Gameplay Ascension boundary (G1)

`constants.ts::isAscensionDeferred(state)` is the sole predicate: `expansionProgress.era !== 'analyst' || expansionProgress.transition !== null`. It is derived after hydration, not a saved flag or additional transition. Any active transition (including recognition while still analyst) and every non-analyst era defer new gameplay Ascension.

`useGameEngine::purchaseUpgrade` checks this before OMNISCIENCE costs, purchase flags, logging or effects. The unchanged definition remains visible at TU >30 and costs 100 TU; ordinary analyst/null purchase, overlay, bonus calculation, NG+ and Sandbox behavior remain original. `Workstation` uses the same helper: at the original TU >=100 threshold the Ops card says ASCENSION DEFERRED / ORGANISATIONAL TRANSFORMATION IN PROGRESS with a disabled control; a visible OMNISCIENCE card is disabled with the explanation even below affordability.

`ascend` refuses direct reset calls during deferral unless `isAscending` is already true, preserving already-open ending choices. Both automatic eligibility handoff and `beginExpansionTransition` refuse to begin while Ascension is open. Return to Sandbox then permits eligible handoff; its original purchased-flag re-entry quirk remains. The eligibility effect observes `isAscending`, so closing an ending retries eligibility even if purchases did not change.

Legacy S1-S3 saves can contain expansion metadata and `isAscending=true`, a mixed state no longer newly reachable through normal G1 play. Hydration/overlay retain it and its existing NG+/Sandbox choices; G1 adds no migration, rollback or provenance flag to distinguish its origin. A mixed-state Sandbox return retains expansion/queue and re-applies deferral; NG+ still uses the original reset contract. `hardReset` remains unchanged and available in Terminal, deleting the save regardless of era. S3 counts/rewards and baseline formulas are untouched. No expansion ending or re-authorization mechanism exists yet.

## Continuous SQL demand (S4)

`GameState.aiReviewDemand` defaults to `{ active: false, arrivalIntervalTicks: 40, nextArrivalTick: 0, totalArrived: 0, totalCompleted: 0 }` plus the three zero-valued S5 proof fields below. Hydration accepts strict boolean true for activity, a positive safe-integer interval, and nonnegative safe-integer schedule/counters; missing/invalid fields use these defaults. S4 activity requires `ai_pilot`, wave three, target `acceleration`, and step `continuous_demand_active` or `pressure_visible` (`useGameEngine::hasContinuousAIReviewDemand`); S5 extends that predicate below. Scores never activate demand. UI availability/countdowns remain derived.

The final finite wave-two completion creates `ai_pilot / acceleration / continuous_demand_offer`, with pending zero/completed six and demand inactive (`completeAIReviewQuery`). A guarded effect recovers a pre-S4 save already at those completed counts; it offers rollout without regenerating six requests. Generic `beginExpansionTransition` applies the same exact eligibility. `Workstation` exposes Review operational rollout; `App` reuses `AIPilotIntroduction` for the positive OPERATIONAL ROLLOUT dialog. “Later” leaves the saved offer unchanged. Existing activity guards defer this management review without pausing ordinary simulation.

`acknowledgeOperationalRollout` alone activates demand, starts wave three at `{pending:4,completed:0,wave:3}`, resets demand proof counters to zero, and schedules `nextArrivalTick = tick + 40`. The transition becomes `continuous_demand_active`; era stays `ai_pilot`. A stale/repeated acknowledgement cannot reset counters or replenish the initial four.

The existing 200 ms engine interval calls `arriveAIReview(prev, prev.tick+1)` against the functional update's latest state. At each scheduled opportunity it adds **one** pending request below `AI_REVIEW_QUEUE_CAP=12` (`constants.ts`), increments `totalArrived` only when added, and schedules the next opportunity 40 ticks later (**8 simulated seconds** at the default interval). At cap it only reschedules: no hidden discarded jobs, penalty or proof count. Arrivals continue through SQL and other activities; existing Ascension/reboot pauses stop the engine. Overdue loaded schedules process at most one opportunity on the next eligible tick and schedule forward; no wall-clock catch-up or offline progression exists.

Wave-three reviews reuse engine-issued IDs tied to wave/completed count and the unchanged editable, correctly prepared SQL request/human EXECUTE path. Arrivals alter pending but leave attempt identity valid. `completeAIReviewQuery` atomically consumes one pending, increments queue completed and demand `totalCompleted`, and pays the original 100 clean/+250 PU with prestige/meeting effects. Manual and one-off S2 callbacks cannot alter demand accounting. Preparing, closing or reloading an unfinished draft consumes nothing; transient IDs are lost on reload, so close the restored manual SQL window and reopen via REVIEW NEXT QUERY to retry.

`continuousDemandProof` runs after automatic arrivals and continuous completions. Both **totalArrived >=3 AND totalCompleted >=3** are required for `pressure_visible`; neither side alone is sufficient. Initial backlog and capped opportunities do not count as arrivals. S4 ends at `ai_pilot / acceleration / pressure_visible`, with routing still active at 40 ticks until S5 acknowledgement. Generic Acceleration establishment remains refused. Save/reload preserves counts, queue, next scheduled tick and step without re-acknowledgement or immediate duplication; the existing two-second autosave window still applies.

Workstation shows active routing and a whole-second approximate countdown from the actual tick schedule. A queued SQL overlay also shows the live pending count, so work arriving during review is visible. No new dashboard, deadline, penalties, AI mistakes, confidence, auto-execution, Velocity metric or external service exists. G1, ordinary rewards/rates/formulas and factory reset remain unchanged.

## Compressed routing and Acceleration (S5)

`aiReviewDemand` adds persisted `acceleratedArrivals=0`, `acceleratedReviews=0`, and `acceleratedPeakPending=0`; `hydrateState` validates each as a nonnegative safe integer. Legacy S4 saves retain their 40-tick cadence/history and default these proof fields to zero. They are scoped experience evidence, not a Velocity score or general telemetry.

Queue pending/completed/wave and totalArrived/totalCompleted remain intact. Stale, premature or blocked acknowledgements do nothing. Deferral leaves S4 routing at 40 ticks.

Proof never recreates a transition in the established era. Acknowledgement closes the local presentation so a later update does not open automatically.

Whole-state autosave retains all proof, pending work, cadence, schedule and steps; no reload auto-acknowledges or establishes an era. Transient SQL drafts/attempts remain discarded without consumption. Workstation adds compact ROUTING: ACCELERATED / ~4s / HUMAN EXECUTION: REQUIRED status. No penalties, deadlines, errors, confidence, batch actions, auto-execution or external service exists. G1 defers Ascension throughout S5 and established acceleration; factory reset remains unchanged.

## Schema exception batches (S6)

`GameState.schemaBatchReview` defaults to `{introduced:false, active:false, batchSize:0, autoMapped:0, exceptionsTotal:0, exceptionsResolved:0, batchesCompleted:0}` (`types.ts::INITIAL_STATE`). `hydrateState` accepts strict true for booleans and nonnegative safe integers for the five counts, defaulting missing/invalid fields to false/zero. It is purpose-specific saved authority; no transient selections, board or attempt identity are persisted.

`isSchemaBatchEligible` requires established `acceleration` with transition null and a true `pandas_scripts` purchase flag. Scores alone never qualify. `schemaFeedbackStep` derives the opt-in SCHEMA MAPPING PILOT introduction while not introduced/active/completed. `acknowledgeSchemaUpdate('schema_introduction')`, guarded by existing activity/overlay rules, creates **2,400 total / 2,395 automatic / 5 exceptions** and sets introduced/active. Deferral changes nothing. No new era transition or unlock modification occurs.

`openSchemaBatchReview` additionally requires the active exact batch, enough raw for the 20-raw reward contract, and no current activity/attempt. The engine issues a transient ID, five unique vocabulary field IDs selected with the existing random-sort selection, and the current completed-batch count. `PandasMappingGame` displays that explicit exception board and an AI BATCH MAPPING header. `RAW_HEADERS`/`CLEAN_HEADERS` now live unchanged in `constants.ts`, shared with the engine; ordinary manual selection, reverse target ordering and matching/mistake behavior remain original. The automatic bulk is assumed correct; the five ambiguous fields are withheld for human matching, not guessed. No confidence model or bad automatic mapping exists.

`completeSchemaBatchReview(attemptId,mappings,mistakes)` validates eligible era/prerequisite, active scale, open Pandas mode, issued ID/count, five unique raw IDs from that board, each mapped to its identical clean ID, nonnegative integer mistakes, and at least 20 raw. Incomplete, wrong, duplicate, stale, unissued or reload-lost reports cannot pay. Completion atomically spends **20 raw**, grants **50 clean × (1+0.1×prestige.level)**, adds **max(0.01,0.05−0.01×mistakes)** quality capped at 1, and writes the original-style mapping log. PU/TU and board-meeting progress are unaffected, as in manual mapping. The thousands are workload-scale representation, not an economic multiplier; this flat review reward deliberately preserves baseline economy. Insufficient raw at payout rejects reward/proof and leaves the batch retryable.

Accepted completion sets active false, exceptionsResolved five, and increments batchesCompleted exactly once. The first completion derives an opt-in BATCH COMPLETE result; explicit `acknowledgeSchemaUpdate('schema_first_result')` creates **12,000 total / 11,995 automatic / 5 exceptions**, preserving completed count one. The second completion stores count **two**, sufficient exception-work experience proof. Workstation shows completion; no third/repeatable/automatically scheduled schema batch is implemented.

Batch matching retains the 1.5-second success presentation but uses its own cancellable timer. `closeSchemaBatchReview` validates the current ID and closes rather than toggles mode; closing before payout resolves nothing and retains the active batch. `App` keys batch presentations by attempt so old completed boards cannot pay a new batch. These protections apply to batch mode; the ordinary manual callback/effect/timer quirks remain preserved. Manual Initialize Schema Mapping stays available, costs/rewards exactly as before, and cannot alter batch proof.

Whole-state two-second autosave preserves introduction, active batch, scale, resolution and completed counts. Unfinished reload loses local board/ID: the saved Pandas window reopens in ordinary manual mode, so close it and explicitly reopen REVIEW SCHEMA EXCEPTIONS to retry the saved batch. Finishing that ordinary board cannot consume/advance the batch. Completed saves neither repay nor silently create another batch. SQL routing continues at 20 ticks while exception mapping is open, retaining cap twelve and no penalty. G1/factory reset remain unchanged. No AI errors, downstream/customer effects, schema writes, auto-approval, MCP, permissions or new era is implemented.

## Product DB read context (S7)

`GameState.connectedEnterprise` defaults to `{productDb:{connected:false,access:'none'},readUses:0,mappingBatch:{active:false,completed:false}}` (`INITIAL_STATE`). At S7 its authority values were **none/read**; S8 extends the exact union as documented below. `hydrateState` retains a connection only when connected is strictly true and access exactly read; any other authority restores false/none, never an upgrade. Read uses require a nonnegative safe integer. Batch flags require strict booleans; completed suppresses active. These are purpose-specific saved fields, not IAM or a tool registry. The single connected batch's scale is fixed in `App`/`Workstation` at **20,000/19,997/3**, rather than additional saved metadata.

An engine effect calls guarded `beginExpansionTransition` only for `acceleration`, transition null, `schemaBatchReview.batchesCompleted >=2`, and no open Ascension. It creates `connected_enterprise / read_connection_offer` while era remains acceleration. Neither scores nor prestige substitutes for S6 proof. `connectedFeedbackStep` derives the opt-in SOURCE CONTEXT presentation; original activity guards defer it. The dialog includes disconnected Product DB status, requested READ, allowed schema/example/metadata inspection, forbidden create/update/delete/execute changes, and CONNECT READ ONLY.
